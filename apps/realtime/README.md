# @jeopardy/realtime

The realtime Worker: WebSocket-only surface owning `GameRoomDO` - one Durable Object per game room, addressed by `idFromName(roomCode)`, speaking the room protocol from `@jeopardy/protocol/room/*`. Since M3, players/displays/hosts connect through the SINGLE ORIGIN (`wss://<web-origin>/room/<CODE>/ws`, forwarded by the web Worker's cross-script binding - docs/decisions/2026-08-13-single-origin-binding.md); this Worker's own `/room/<CODE>/ws` route remains for ops/debug and direct-worker testing.

What the DO does (`src/game-room-do.ts` + the pure modules under `src/room/`):

- **Explicit lifecycle**: rooms exist only after the typed `POST /initialize` RPC (reachable exclusively through the DO binding - the public router forwards nothing but WS upgrades). Uninitialized or expired codes refuse upgrades with `no-such-room`; an idle-expiry alarm (limits.room.idleExpiryMs) wipes the room and frees its code.
- **The engine feed**: relayed actions are authority-checked (`room/authority`), stamped with server arrival time + session identity (`src/room/engine-glue.ts`), run through `@jeopardy/engine`'s `transition`, persisted, and narrated as redacted event batches (`src/room/redact.ts` - phones never receive Daily-Double locations, secret final wagers, or others' typed answers). Exactly one room-level `buzz-won` per arming carries the resolved room-audible sound (team's in teams mode); `buzz-rejected` goes to the one phone it concerns and never rides the public stream.
- **Buzz latency compensation (M6)**: arming opens a window (`src/room/arm-window.ts`), broadcasts `arm-window` with its id, and HOLDS the arming's buzzes for a few milliseconds; every client's `arm-ack` measures that connection's round trip, and the held presses reach the engine ranked by credited reaction time (`@jeopardy/protocol/room/buzz-fairness`) with each action stamped at its credited press time. Reordering is strictly UPSTREAM - the engine still receives one ordered list (docs/design/expansion-and-boundaries.md boundary 2.1) - and the window is STORAGE plus an alarm-book deadline, because eviction between the arm and the press must not lose a buzz. Held presses flush before any other action reaches the engine, so a buzz-window timeout can never kill a clue somebody rang in on. Off (`settings.buzzing.latencyCompensation`) restores M3's arrival order. Threat model and the clamp that bounds a lying client: docs/decisions/2026-08-17-buzz-latency-compensation.md.
- **Timer hints -> alarms**: engine `timer-set` events become scheduled expiry actions in a multiplexed alarm book (`src/room/storage.ts`) alongside leader-disconnect succession checks, the buzz-adjudication deadline, and the expiry deadline. The book is pruned by phase after each transition (`timerLiveInPhase`), so a stale entry neither wakes the DO nor shows up as a phantom countdown on the `timers` a snapshot carries.
- **Recovery (M6-hardened)**: every snapshot carries the room's live `timers` (remaining ms) and, during an open arming, is followed by the `arm-window` - so a phone that slept mid-clue and a console reopened on another laptop both resume to the exact screen, countdown included, and can still race. The reconnection matrix is `test/reconnection.test.ts`.
- **Sessions**: players get a server-minted seat (`p-<n>`) plus a secret resume token; `resume` restores the exact seat on a fresh socket. Roster + team docs (the two customization tiers) live in DO storage, hibernation-safe; the engine only learns seats at `start-game` (lobby stays team-fluid).

Storage layout is documented at the top of `src/room/storage.ts`. Hard boundary: transport is partyserver, hibernation enabled - transport ONLY; game logic and the `src/room/*` modules never import partyserver types (docs/decisions/2026-08-13-partyserver.md).

Tests run inside workerd (`@cloudflare/vitest-pool-workers`) against the real DO - including forced instance eviction (`evictDurableObject`) mid-game and alarm firing (`runDurableObjectAlarm`); `pnpm test` here regenerates `worker-configuration.d.ts` first. Bot players from `@jeopardy/bots` drive the game-flow suites over real sockets. `pnpm build` is a `wrangler deploy --dry-run`; real deploys are owner-run (docs/cloudflare-setup.md).
