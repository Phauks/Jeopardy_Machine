# 2026-08-13 - PWA as an underlying design assumption

## Decision

The app is built as a Progressive Web App from M0 onward - but "PWA" means something different per surface, and the guest-friction rule outranks it everywhere.

| Surface              | PWA posture                                                                                                                                                                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Creator / editor** | Full PWA: installable, works fully offline (library + editor are local-first anyway), desktop-app feel. The flagship beneficiary.                                                                                                                    |
| **Host console**     | Installable + app-shell cached for instant load and resilience on venue Wi-Fi. Live play still requires network (the DO is the game); offline hosting is not a goal.                                                                                 |
| **Board display**    | App-shell cached (fonts, sounds, theme assets precached = no mid-game asset stalls).                                                                                                                                                                 |
| **Player buzzer**    | PWA tech, invisible. Service worker makes loads instant on bad Wi-Fi, but players are NEVER shown an install prompt - scan-and-play in the browser tab is sacred (guiding principle 3). Wake lock, vibration, and fixed layout all work uninstalled. |

## Architecture consequences

1. **Service worker from M0** (SvelteKit's `$service-worker` module): precache hashed immutable assets (JS/CSS/fonts/sounds); **network-first for all HTML/navigation** so nobody plays on a stale app shell.
2. **Version-skew policy**: the SW must never let a cached client talk a stale protocol to a live room. The WS hello already carries protocol version (refuse + prompt reload on mismatch); the SW updates on navigation, never mid-game (`skipWaiting` only on join/landing routes, not inside an active room).
3. **Local-first storage becomes IndexedDB-first** (library, content packs, pending media) rather than raw localStorage - the M1 repository interface targets IndexedDB; localStorage only for tiny prefs/session tokens.
4. **Web manifest** per surface entry point (one manifest, `display: standalone`, scope-aware start URL); install UI is surfaced ONLY in creator/host contexts.
5. **Offline boundary is explicit in UX**: editor offline = full function; console/buzzer offline = clear reconnect states (already specced in docs/design/user-flows.md A5/C6). No fake offline play.

## What this does NOT mean

- No install nagging, anywhere, ever. Install is discoverable, not pushed.
- No offline multiplayer ambitions. The room is authoritative and online by definition.
- No native app wrappers; the PWA is the "app".

## Milestone placement

- **M0**: manifest + SW skeleton with the caching policy above; documented in DEVELOPMENT.md (added to M0 scope 2026-08-13, same-day as approval).
- **M1**: IndexedDB-backed repositories.
- **M4**: precache manifest grows to fonts/sound pack; install affordance in editor chrome.
- **M5**: dress-rehearsal checklist includes airplane-mode editor test + SW-update-during-game drill.
